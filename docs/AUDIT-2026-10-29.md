# Keydial Commander review

Date: 2026-10-29

## Review scope

Reviewed the Python device/input/action/control path, profile persistence and validation, React interface and state, tests, desktop shell, systemd/udev installation, package metadata, distribution scripts, Nix setup and existing design/worklog/roadmap. Dependencies, generated assets and screenshots were treated as supporting material, not project source. No physical device was captured, no running service was reconfigured, and no user profile was changed during the review.

The app is a K20 remapper on Linux, with a local control interface. It is not yet a generic peripheral abstraction. KeyCommand's game and shared score service are being built separately, with an importable game preset as the first integration.

## Actual system map

| Area | Current implementation |

| Physical input | `evdev_source.py`, `input_map.py`, `input_translator.py`; exclusive event-node grab, K20-specific mapping, two-second hotplug rescan |
| Output/actions | `action_engine.py`, `uinput_handler.py`; shortcuts, held modifiers, macros, argv commands, profile switching |

| Live state/CLI | `keybind_manager.py`, `ipc.py`, `keydialctl.py`; memory map, private runtime socket, framed JSON |
| API/events | `api_server.py`, `event_bus.py`; aiohttp REST, bounded event fan-out, WebSocket, static SPA |
| Interface | React/TypeScript/Vite, TanStack Query, Zustand, dnd-kit, CSS variables, fixed K20 stage |
| Shell/deployment | GTK3/WebKit2 wrapper, user systemd service, uaccess rules, partially maintained distribution builders |
| Game reuse | Profile format and K20 mapping are useful; remapping events lack physical source identity and timing |

## Issues fixed in this update

1. Shortcut capture committed Ctrl or Shift immediately on keydown, so ordinary chords could not be entered naturally. Capture now waits for a primary key, or commits modifier-only combinations on release. Capture state resets on focus/context changes.
2. Dragging an unfinished action template sent an invalid binding before the user could configure it. Templates now stage a draft. Clicking also stages a template for the selected control; Save performs the write. Drafts are scoped by profile and control.
3. The synthetic evdev integration test used normal discovery, which could also grab a connected real K20. Its discovery is now restricted to the synthetic node.
4. HTTP and WebSocket requests had no browser-origin guard. A nonlocal browser page could attempt to invoke the command-capable local API. Loopback Host and Origin checks now reject such requests, while allowing the local UI, Vite development UI and CLI.
5. The main architecture document described deleted Bluetooth modules and the wrong permissions model. It now describes the actual evdev implementation and the game boundary.

## Remaining findings

### Packaging and install reliability

* The README's fresh-install order builds the Python wheel before the ignored frontend assets exist. Building the web UI later updates the checkout, not the installed wheel. Build frontend assets before packaging and verify the wheel contents.
* `make install-all` writes `/usr` and `/etc` without elevating those steps; only its udev target invokes sudo. Its user-service installation reloads the system manager instead of the user's manager.
* Arch and Nix reference removed unbind/udev files and stale dependencies. Nix omits current Python runtime dependencies.
* Debian rules fail parsing with `missing separator`, and the build directory layout needs repair. RPM references a spec file absent from the repository.
* Distribution builders do not consistently build/include the GUI and shell. Current packaging tests mostly check strings and versions rather than installed behavior.

These paths need a focused packaging milestone. This update does not claim that distribution packages can be built or installed successfully.

### Driver behavior and validation

* Dial sensitivity is persisted by the UI and profile store, but the current evdev translation path emits one pulse per wheel event without applying the saved sensitivity. The old accumulator claim belongs to the removed input layer.
* Commands and macros are awaited by the input dispatch path. Long macros can delay processing and event feedback for that node.
* Device removal drops the node without resetting translator state until full shutdown. Held/chord state and virtual key release need focused lifecycle regression tests before changing behavior.
* Profile imports skip invalid bindings and can create a partially imported profile. Non-mapping YAML and malformed API object shapes need stricter validation and predictable errors.
* CLI binding validation still assumes a key list, so the full GUI action model is not consistently available through the socket command.
* The API advertises the configured port rather than inspecting the actual bound socket when configured with port zero.

### Interface and support claims

* Battery display, installed-app selection, automatic per-app profiles and tray behavior in older specifications are not all implemented.
* The fixed three-column Commander layout and dialogs need a separate accessibility/responsiveness pass. The new game does not inherit these constraints.
* Physical Bluetooth behavior was verified in the historical worklog. USB's input path exists but physical USB verification is still outstanding.
* Troubleshooting, Arch and Nix docs still contain blanket input-group guidance and references to removed utilities. Use the current uaccess rule and source architecture when reconciling these documents.

### Permissions and game integration

The existing daemon owns remapping and can run user programs. Its udev permissions are desktop-session access, not website consent. The new browser game must not silently enumerate devices, read system-wide input, or treat an observed model as proof of input attribution. No public endpoint or live game-to-daemon bridge was added.

## Environment and checks

The checkout's `.venv` records Python 3.12 but its executable resolves to Python 3.14, so it cannot import its installed test dependencies. Verification uses a fresh temporary environment instead of changing the user's environment. Sandbox-only attempts to run socket servers are not a valid application baseline; full regression checks need local socket access and a temporary `XDG_RUNTIME_DIR`.

Frontend regression fixtures never connect to the real daemon. Hardware-dependent input capture is excluded from routine verification. Final test counts and outstanding limitations are recorded in the delivery notes after the checks finish.

## Next milestones

1. Keep Commander reliable as a local remapper and fix packaging in a dedicated release.
2. Ship KeyCommand as a separate browser app with actual shared scores, explicit metadata permissions, and self-reported peripheral categories.
3. Test physical peripherals and browser combinations before making device support claims.
4. Design a paired, revocable, selected-device input bridge only if casual key remapping no longer meets the game's needs.
